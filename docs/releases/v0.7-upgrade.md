# Extrio 1.0 Upgrade and Restore-Based Rollback

## Scope

This procedure covers single-organization SQLite and PostgreSQL 16 instances.
The target is the unpublished `v1.0.0` candidate (schema 013), with status
`Needs_Review`; no stable image or tag is available for production installation.
The source baselines are:

| Source | Exact commit | Schema | Evidence status |
| --- | --- | --- | --- |
| Published `v0.7.0-alpha.1` | `1e02dbbddd273bda7a7023b8824d0bb58f3db5d6` | 010 | Upgrade and full-backup rollback passed for RC on both databases |
| Published `v1.0.0-rc.1` | `c2fc06f420c31aaf5bbbea53332ef4af2b48804e` | 013 | Source-to-stable upgrade, full restore and matching-source rollback passed focused tests on both databases |

RC publication and exact-SHA checks are recorded in the [RC release record](v1.0-rc.1.md).
The Alpha path establishes Delivery identity, durable login throttling, and versioned
runtime backfills. RC and the stable candidate share schema 013, so the RC path must
preserve migration history as well as immutable versions, bindings, signatures,
Deliveries, users, sessions, Artifacts and keys. An unchanged schema number does not
replace a restore rehearsal. Current results and gates are in the
[stable handoff](v1.0.0.md) and [release validation](../reviews/v1.0-stable-2026-09-27/release-validation.md).

There is no in-place down migration. Stable release, image publication and live
deployment require separate user authorization; this procedure grants none.

## Preconditions

1. Pause schedules and record queued, running, and delivering work.
2. Stop API, Worker, and MCP processes.
3. Create and verify a full offline backup with the source release:

```bash
uv run --project backend extrio-backup /secure-backups/extrio-pre-v1 --offline
```

4. Rehearse restore and upgrade into an empty SQLite path or empty PostgreSQL database.
5. Keep the source and target program versions and image digests, contract bundle,
   tenant ID, and signing key ID. For published RC images, obtain the backend/web
   digests from its Release attachment `release-verification.json`; use neither
   `latest` nor a local rebuild as proof of installing that published artifact.

## Upgrade

Run the migration job once against the intended database. Runtime services do not migrate by
default.

```bash
uv run --project backend extrio-migrate
```

The migration establishes:

- one Delivery for each `(itemEventId, sinkVersionId)` pair;
- deterministic `sha256:` IDs for new Deliveries and DeliveryAttempts;
- a shared database-backed login-attempt window.
- a `data_migrations` completion registry and an index for pending schedule dispatches.

Historical compatibility fields and attribution are backfilled in batches of at most 200 rows.
Existing values and record timestamps are retained; missing nullable/default response fields are
filled without rewriting signed rules or attestations. Completion is recorded only after every
batch succeeds. Retry an interrupted migration with the same command; runtime startup refuses
incomplete backfills and `extrio-doctor` reports `data_migrations_pending`.

The migration command requires stopped instance processes and acquires the offline instance lock.
SQLite validates foreign keys before committing each schema migration, including its version marker.
Ordinary runtime restarts check versions and completion markers without scanning historical payloads.

Review legacy `claimed` schedule occurrences against existing Runs before resuming schedules. Old
dispatches lack an atomic receipt, so a missing `run_id` alone does not prove that no Run was created.
Current dispatches commit Run/Operation/Job and the occurrence receipt together; interrupted work
remains retryable, while paused or revised schedules are explicitly skipped.

Historical Delivery and DeliveryAttempt IDs remain unchanged. Records created before SinkVersion
identity existed receive a stable `#legacy-...` version marker and must not be treated as proof of
the historical Sink configuration.

Start API and Worker from the same release only after migration succeeds. Verify `/readyz`,
`extrio-doctor`, login, rule attestations, item lineage, queued work, and pending Deliveries before
resuming schedules.

## Rollback

Migrations are forward-only. Roll back by deploying the matching source artifacts and restoring
the verified pre-upgrade full backup into a new empty target. Never point the source release at an
upgraded database and never overwrite a live instance during restore.

The release gate in `backend/tests/test_release_upgrade.py` covers the published RC,
published Alpha and the September 9 baseline using the actual source commit, not
current code imitating an old database. The RC handoff records six passing
SQLite/PostgreSQL Alpha/historical cases; the stable candidate must rerun those cases
and add RC-to-stable upgrade, full backup, empty-target restore and matching-source
rollback. The stable focused run passed all three baselines on both databases,
with 26 passing upgrade/package/Compose-script checks and no skips. Both databases
also passed installation and authenticated smoke checks using the published RC
digests without rebuilding, as recorded in [integration verification](../reviews/v1.0-stable-2026-09-27/verification.md).
Full candidate regression, local stable images and remote release checks are separate gates. Full backup
integrity and restore failure recovery are covered by
`backend/tests/test_full_backup.py`. PostgreSQL 18 is outside the verified deployment matrix.

## Isolated Published-Image Verification

The verification script uses owned temporary projects and volumes and removes them
on exit. It is not the procedure for upgrading a live instance. To validate the
published RC without rebuilding, use the digests verified from its Release attachment:

```bash
EXTRIO_BACKEND_IMAGE='ghcr.io/iiwish/extrio-backend@sha256:0f841772c0dc5c45f7575203fb0fc599162fd16a40d64e5686869ce083bcb6af' \
EXTRIO_WEB_IMAGE='ghcr.io/iiwish/extrio-web@sha256:c693d8f48f491655820bfbbf6fc583ef8b9ca425a7814d7531521c024bca2981' \
bash scripts/verify-compose.sh --image-only
```

For the PostgreSQL 16 variant, also set `EXTRIO_E2E_COMPOSE_FILE=compose.postgres.yaml`
and `EXTRIO_AUTH_COOKIE_SECURE=false` for this isolated loopback HTTP smoke test only.
The image-only mode requires both digest references, accepts only the repository's
two reviewed Compose files and uses `--no-build --pull always`; it never falls back
to a local rebuild. The no-argument mode retains source-build verification. Syntax
checks do not authenticate arbitrary image digests; the release record is required.
