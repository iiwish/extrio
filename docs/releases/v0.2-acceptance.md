## 2. 发布目标

v0.2 必须证明 Extrio 可以把一个支持范围内的 Source 从数据意图推进到已审核的 RuleVersion，并在不调用 LLM 的运行时中持续采集、规范化、交付、告警、回放和审计。

发布以可运行的纵向闭环为标准，不以对象页面或接口数量为标准。

## 3. 进入验收条件

1. [`../SSOT.md`](../SSOT.md) 权威矩阵中的 v0.2 文档均为 `Confirmed`。
2. 数据库迁移、`extrio.control-plane.v1` OpenAPI、GatherSpec Schema、Worker runtime 和 UI 版本已经冻结为候选版本。
3. 所有自动化测试在与生产同类的环境中执行。
4. 测试 Tenant、Source、Kafka、Webhook、对象存储、Secret Manager 和故障注入能力可用。
5. 每个候选构建具有不可变制品 digest、依赖锁、SBOM 和部署记录。

## 4. 阻断条件

以下任一条件存在时不得发布：

- 跨租户读取、写入、执行或对象引用。
- 凭据明文进入 URL、规则、Redis、日志、Artifact、ArtifactManifest 或输出。
- Published RuleVersion 可被更新，或 Worker 可执行 digest/RuleAttestation 无效的规则。
- 运行期可访问 LLM 或执行用户代码。
- Source SSRF 可到达内部网络、metadata 或未授权主机。
- 重复调度、Worker 恢复或队列重建产生不同逻辑 ItemEvent/Delivery。
- 采集失败、预算耗尽或必填质量门失败被显示为完整成功。
- 生产回放没有额外授权或可以越过默认无副作用边界。
- P0/P1 缺陷未关闭；高危已知漏洞未修复或未获有期限风险批准。
- 设计容量、RPO/RTO 或关键用户旅程没有真实证据。

## 5. 端到端验收场景

### `AC-001` 创建并冻结 CollectionVersion

**映射：** `US-001`、`FR-001`、`FR-002`

1. CollectionEditor 从 Published TemplateVersion 创建 Collection，并修改允许的字段和质量门。
2. 缺少身份字段、无效 Schema 和未声明输出字段必须被拒绝并定位到具体字段。
3. 有效版本完成验证并冻结。
4. 冻结版本无法更新；变更操作创建新 CollectionVersion。

**证据：** API/UI 旅程测试、Schema/语义反例测试、数据库不可变约束测试和 AuditEvent。

### `AC-002` 批量接入 Source 与访问边界

**映射：** `US-002`、`FR-003`、`FR-004`、`FR-014`

1. 导入至少 100 个 Source，其中包含 HTTPS、获批匿名公共 HTTP、未获批 HTTP、重复 URL、非法协议、跨 Tenant AccessProfile 和未授权域名样本。
2. 系统返回逐项结果，合法项建立 SourceRevision 与 Collector，非法项具有稳定错误码。
3. SourceRevision 固定 entrypoint、allowedHosts、transport、速率、体积和合规依据。
4. 匿名公共 HTTP 只有在 TenantAdmin 策略显式接受风险时可以建立 Source；任何 AccessProfile 或凭据请求仍必须使用 HTTPS。
5. 任何 secret 明文均不能进入 Source、Collector 或导入错误报告。

**证据：** 批量导入测试、Tenant 隔离测试、secret 扫描和逐项结果快照。

### `AC-003` 编译、验证、发布与回滚

**映射：** `US-003`、`FR-005`、`FR-006`、`FR-015`、`NFR-001`、`NFR-002`

1. 编译以 Source 样本和 CollectionVersion 为输入，由默认模型产生合法 `extrio.rule-plan.v1`，平台验证后产生 GatherSpec、编译谱系、ArtifactManifest、样本 Artifact、字段预览和质量报告。
2. 非法 selector、外部 `$ref`、敏感 Header、越界 URL、缺失身份和不支持 runtime 规则不能进入 NeedsReview。
3. CollectionEditor 无法发布；RuleReviewer 批准后发布事务原子切换活动版本。
4. 仅拥有 TenantAdmin 的用户无法发布、回滚、reprocess 或 redeliver；多角色用户必须显式满足对应角色。
5. Run 创建后发布新版本，该 Run 仍使用旧版本。
6. 回滚只切换活动指针；历史 GatherSpec、digest 和 Run 不变化，无当前有效证明时先追加 RuleAttestation。
7. RuleAttestation 签名绑定 approval、review policy 和 evidence digest；任一字段篡改均被拒绝。
8. SigningKey Retired/Compromised 与重新证明按合同阻断或恢复新 Run，不修改 RuleVersion。
9. Collector 名称修改保留活动规则与可运行状态；采集意图或 Source 入口修改清除当前候选并阻断新 Run，直到新候选完成审核发布，历史 RuleVersion、RuleAttestation 与 Run 均不变化。
10. 规则编辑表单按执行顺序集中展示可修改的列表 Item selector、可编辑网页业务字段 selector、分页参数、`detailUrl` 交接和输出字段 selector；系统管理字段不进入编辑表单；不可编辑的请求配置、字段语义、安全边界和输出合同只在 JSON 中按需查阅，不在表单重复展示。直接编辑两个阶段的 selector 或分页参数时，系统创建受控 Override 和新候选 digest，清空旧审核决定，并使用最近探索样本完成 GatherSpec Schema、详情发现和必填字段质量验证；字段语义保持 CollectionVersion 锁定，验证失败不能进入可发布状态。

**证据：** 权限测试、规则 fixtures、事务故障注入、RuleAttestation/密钥事故验证和并发发布/触发测试。

### `AC-004` HTTP page 型 list/detail 运行

**映射：** `US-004`、`FR-007`、`FR-009`、`FR-010`

1. 使用多页 HTML fixture，list 提取列表标题和 detail URL，detail 提取详情标题、发布时间和正文，Run 写入采集时间。
2. 重复页、空页、最大页数、超时和响应过大均按合同结束。
3. 相同响应重复执行产生相同 entityKey、outputContractDigest、payloadFingerprint、revisionKey 和 eventId。
4. 内容或输出合同变化创建新 Revision；未变化默认不创建新 ItemEvent，但每个有效 Run 创建 HarvestObservation。

**证据：** golden fixtures、属性测试、预算测试、运行统计和谱系查询。

### `AC-005` next_link 与受限浏览器运行

**映射：** `FR-007`、`NFR-001`、`NFR-008`

1. next_link 在 allowedHosts 内正常翻页，循环链接被检测并停止。
2. 跨未授权主机、DNS rebinding、私网地址和 metadata URL 被阻断。
3. 获批匿名公共 HTTP 可在无凭据边界内运行；携带 AccessProfileVersion 或凭据的请求只能使用 HTTPS。redirect 不继承凭据、不能降级，并对目标重新执行 exact origin/path scope。
4. 浏览器上下文按 Run 隔离，下载和内部网络不可用，结束后无 cookie/local storage 残留。
5. Worker 不能访问 LLM 或执行规则外代码。
6. browser Rule 固定 engine/version、viewport、locale、timezone 与 Unicode 版本；回放消费 canonical DOM snapshot，不重新执行 JavaScript。

**证据：** SSRF 套件、浏览器隔离测试、网络策略测试和进程资源报告。

### `AC-006` 调度、租约、取消与恢复

**映射：** `FR-008`、`FR-009`、`NFR-003`

1. 双调度器处理同一 occurrence 只创建一个 Run。
2. Worker 在处理中失联，新 Attempt 接管；旧 Worker 因 fence token 无法提交。
3. 取消和超时保留 staging 与证据并明确标记不完整，不提升生产 ItemEvent 或 Delivery。
4. v0.2 固定 overlapPolicy=forbid。支持范围内的时间降序 `next_link` Source 必须固定 CollectionPolicyVersion、运行窗口与 Checkpoint 前值；仅成功终结推进 Checkpoint，预算截断、部分成功、失败、取消和超时保持原值。

**证据：** 并发测试、进程终止故障注入、状态机测试、Checkpoint 原子提交测试和预算截断反例。

### `AC-007` Item 与幂等一致性

**映射：** `FR-010`、`NFR-002`、`NFR-003`、`NFR-006`

1. 相同身份、输出合同和内容在请求重试、Attempt 重试和队列重复下只创建一个 Revision/Event，每个 Run 仍有唯一 Observation。
2. 身份为空或类型转换失败按 onError 处理，不产生不稳定 entityKey。
3. Source 缺失历史实体不会自动产生 tombstone。
4. 相同 payload 在 outputContractDigest 变化后产生新的 revisionKey，旧 Revision 不被覆盖。
5. 同一 Run 的同 entityKey/same revision 重复项合并并记录 occurrenceCount；不同 revision 产生 `ITEM_IDENTITY_CONFLICT`，不按完成顺序覆盖。
6. 从 ItemEvent 可追溯完整规则、观察、运行、数据合同、Source 和 ArtifactManifest。
7. A→B→A 与 tombstone→恢复产生新的转换 eventId；同一转换重试复用 eventId。
8. 质量门、duplicate conflict 和 Run outcome 在 Delivery outbox 释放前完成；Failed/Cancelled/TimedOut 不产生可发送 Delivery。

**证据：** 幂等压力测试、数据库唯一约束测试、谱系查询和数据丢失核对报告。

### `AC-008` Kafka 与 Webhook 交付

**映射：** `FR-011`、`NFR-003`、`NFR-006`

1. Kafka message key 为 eventId，Kafka 与 Webhook body 均通过 ItemEvent Envelope Schema，并包含 deliveryId 与完整谱系。
2. Webhook 具有 Idempotency-Key、Content-Digest、时间和域隔离 HMAC 签名；篡改 body、timestamp 或 digest 均失败。
3. `429/5xx` 重试，永久 `4xx` 直接失败，UnknownOutcome 复用同一 deliveryId。
4. 超过窗口进入 DeadLettered 并告警；Run 采集状态不被改写。
5. 同 SinkVersion 人工 redelivery 复用 Delivery/deliveryId 并追加 RedeliveryRequest/Attempt；新 SinkVersion 创建新 Delivery。
6. 新绑定 SinkVersion 在下一次有效 Observation 时为既有 ItemEvent 创建缺失 Delivery，不创建伪造的新事件。
7. DeadLettered redelivery 成功后 Delivery 进入 Delivered，失败仍保持 DeadLettered；Delivered redelivery 由 Request 独立记录且不回退原状态。

**证据：** Sink contract test、模拟故障、重复检测、签名验证和 DeadLettered 告警。

### `AC-009` Artifact 与三种回放

**映射：** `US-006`、`FR-012`、`FR-014`

1. metadata_only、sampled 与 replayable 模式具有互斥字段和明确 completeness；rawRetentionDays=0 不得生成伪 replayable 证据。
2. validate_only 无 HarvestItem、Delivery、生产 namespace 或 Sink 副作用。
3. reprocess 需要审批并记录 replay lineage，默认不交付。
4. redeliver 不重新请求 Source，保留 eventId/deliveryId 并记录审批与新 Attempt。
5. 只有完整 replayable Manifest、连续 chunk 与全部有效 Artifact 可以证据等价回放；缺失、断序、digest 错误、跨租户或过期均拒绝。
6. 100,000 item 和大批 list/detail 响应通过上限 1,000 条的 chunk 扩展，root manifest 不内嵌全部响应。

**证据：** 副作用断言、RBAC 测试、对象生命周期测试和 AuditEvent。

### `AC-010` 漂移、告警与恢复

**映射：** `US-005`、`FR-013`、`FR-015`

1. 前 3 个成功 Run 标记 BaselineBuilding；安全/强制质量异常立即告警，历史分布阈值只在 BaselineReady 后使用。
2. 连续 3 次 Failed 自动暂停 Schedule，不自动生成或发布规则。
3. 新样本、新 RuleVersion、人工审核、金丝雀 Run 和活动版本切换构成完整恢复路径。
4. Schedule 间隔不超过 12 小时时在 2 个计划 Run 且最长 24 小时内发现漂移；更低频 Schedule 只按 2 个计划 Run 验收。
5. 告警链接到可操作对象和证据，通知中不包含敏感 URL 或凭据。

**证据：** 基线 fixture、告警规则测试、恢复旅程和无自动发布断言。

### `AC-011` 认证、审计和安全边界

**映射：** `FR-014`、`NFR-008`、`NFR-013`

1. 新实例只允许原子创建首个本地管理员，密码以 Argon2 哈希保存，不提供公开注册入口。
2. 未认证控制面请求被阻断；会话只在服务端保存 token 摘要，并可通过退出立即吊销。
3. 登录使用通用失败响应并限流；跨 Origin 状态变更被阻断，Cookie 使用 HttpOnly 与 SameSite。
4. 规则发布写入真实认证 actor 的不可变 AuditEvent，客户端对象 ID 不能绕过资源边界。
5. 外部 OIDC、多用户 RBAC、MFA step-up、Tenant 删除和独立工作负载身份不属于公开 Alpha 的生产能力声明。

**证据：** 认证 API 测试、会话吊销测试、登录限流测试、审计 actor 断言、容器 E2E 和 secret 扫描。

### `AC-012` Schema、协议和 Runtime 兼容

**映射：** `NFR-009`、`NFR-011`

1. GatherSpec、RuleAttestation、ArtifactManifest/Chunk、JobEnvelope、ResultBatch、PlatformError 与 ItemEvent Envelope Schema 通过 Draft 2020-12 meta-schema，正例通过校验。
2. normalizedItemSchema 外部 `$ref`、高复杂度或非 RE2 pattern 由离线语义校验拒绝。
3. FastAPI 控制面、Python Worker 与 TypeScript validator 对 Unicode、canonical HTML、Browser DOM snapshot、canonical bytes、outputContractDigest、ruleDigest 和 signature fixtures 完全一致。
4. 未知字段、未知 enum 和不支持 runtime 在 Source 请求前被拒绝。
5. OpenAPI 与四类平台消息 consumer contract test 通过，覆盖签名、过期、nonce、audience、旧 fenceToken、跨租户、断链/重复 batch 和事件链；错误具有稳定码、JSON Pointer 和 requestId。

**证据：** Schema 报告、跨语言 golden test、协议兼容报告和错误快照。

### `AC-013` 容量、SLO 与灾备

**映射：** `NFR-004`、`NFR-005`、`NFR-006`、`NFR-007`、`NFR-010`

1. 在产品合同设计容量下，调度延迟、运行吞吐、交付积压和数据库资源满足目标。
2. Redis 全量丢失后从 PostgreSQL 重建工作，不创建新逻辑副作用。
3. PostgreSQL 和对象存储恢复演练满足 RPO/RTO。
4. 指标后端没有 Run、Item、URL 等无界高基数常驻标签。

**证据：** 负载报告、队列重建报告、恢复演练、数据核对和指标基数审计。

### `AC-014` 关键界面可访问性

**映射：** `NFR-012`

Collection 创建、Source 导入、规则审核、Run 详情、异常处置和回放确认必须支持键盘导航、可见焦点、语义化标签、非颜色唯一状态表达和 WCAG 2.2 AA 对比度。

**证据：** 自动化 accessibility report、键盘人工检查和核心视口截图。

### `AC-015` 第一版前端闭环

**映射：** `FR-001`、`FR-005`、`FR-006`、`FR-009`、`FR-010`、`FR-019`、`NFR-011`、`NFR-012`

1. 用户从全部需求列表进入时默认定义新需求，从具体需求筛选上下文进入时默认选中并复用该需求的采集意图与 CollectionVersion，只补充采集入口 URL；两种模式可切换；每个 URL 具有独立校验和逐项创建/拒绝结果，合法 Source 的 Collector 不因同批非法项回滚；同批成功 Collector 返回并共享稳定 `collectionId`、`collectionName` 与 CollectionVersion。
2. FastAPI 符合 `extrio.control-plane.v1`，探索与 Run 以 `202 Accepted` 返回持久化 Operation；Crawl4AI 固定网页证据，默认模型为 `single` 或 `list_detail` 编译 RulePlan，服务端将其中的 HTML CSS/JSON JSONPath、`page`/`next_link` 分页、detail URL、输出字段、身份与指纹转换成通过 `extrio.gather.v1` 校验的 GatherSpec。
3. 用户可审核 accepted/rejected 样本、确认发布不可变 RuleVersion、Ed25519 RuleAttestation 与 AuditEvent，并从发布成功状态触发立即运行。
4. Run 详情顶部栏提供返回运行列表入口，以 Source 根 URL 和终态作为首屏主信息，以完整入口路径、开始时间、耗时和执行模式作为次级信息；同域名下的不同入口可通过路径区分，页面不显示无信息眉题或 Run ID。顶部 Tabs 分别组织结果、执行过程、范围与增量、质量与证据，并与 Collector 详情统一为全宽等分线型导航。结果摘要在一行内展示结论、接收与拒绝、数据变化和耗时。页面根据 collectionMode 明确展示直接采集或列表分页、detail URL 发现、详情采集、finalizing 和终态；Operation 支持 succeeded、failed、cancelled、timed_out，刷新后继续读取同一任务。完成后展示至少 3 个 accepted Item、1 个 rejected 候选及质量统计。
5. Crawlee 直接解释已发布 GatherSpec，并按冻结的 selector、分页预算与允许主机约束生成 accepted/rejected 结果；accepted Item 展示 RuleVersion、CollectionVersion、SourceRevision、Run、Observation 与 Artifact 的完整 lineage，rejected 候选的 Revision 与 Observation 为空并显示“未生成”，本地 sampled Artifact 不描述为生产证据。
6. `/`、`/collectors`、`/runs`、`/items`、`/settings` 及对象详情可直接访问；顶部栏只显示当前一级页面标题，不显示工作区名称或层级分隔。`/` 展示实际运行成功率、已发布规则覆盖、最新实体质量通过率、最近运行数据量与终态趋势，并只保留最多三项异常入口；不得重复 Run 或 Item 列表，不展示技术 ID、推断式质量分或继续工作入口。待处理判断基于 Collector 生命周期与最近 Run 的真实异常终态，健康已发布 Collector 不得误报。Collector、Run 与 Item 列表直接使用“单行顶部工具栏、固定列运营列表”，三个详情使用“对象标题、结果或配置主卡、内容卡、证据卡组”。Collector 工具栏在一行内提供状态筛选、需求筛选和最右侧新建操作，不显示需求标签、布局切换、重复页面标题或概览指标卡；状态和需求写入 URL。Run 工具栏在一行内提供状态筛选、按 Collector 名称或 Run ID 搜索、排序提示和刷新，不显示重复页面标题或概览指标卡；状态和搜索写入 URL。Item 工具栏在一行内把 Source、Collector 与质量决定筛选放在左侧，把标题、正文、Collector 或 entity key 搜索放在右侧，不显示重复页面标题或概览指标卡；筛选和搜索写入 URL。设置固定在侧栏底部，设置页不显示重复标题、说明栏或供应商/模型平级 Tabs；顶部左侧提供唯一默认模型，右侧提供添加供应商，不展示数量统计，模型按所属供应商分组并可在组内管理，密钥解析状态逐供应商展示，浏览器和 API 不出现密钥明文。侧栏不重复显示工作区信息卡或 API/Mock 环境提示，阶段与 lineage 可保留语义连接线。桌面 `1440x900` 与 `1280x800` 视口无关键溢出或操作遮挡，键盘焦点可见。低于 `1280px` 的窄屏和移动端不属于当前验收范围。
7. 字段风险具有明确的接受、排除或待决策状态，待决策字段阻断发布，处置后警告切换为已解决状态；Collector、Run、RuleVersion、RuleAttestation 与 Item lineage 的版本一致，演示数据与 Source 场景一致。
8. Collector、Run 与 Item 筛选真实生效并写入 URL；Collector 需求筛选器支持输入需求名称或合同版本实时搜索选项，选择结果后关闭弹层并更新 URL。Collector 固定列列表展示 Source 身份、所属需求、状态、活动规则、最近运行和下一步，并使用真实最近 Run 计算健康和下一动作。Run 固定列列表展示身份、终态、接收与拒绝数量、执行模式与范围、停止原因、开始时间和耗时，并支持按 Collector 名称或 Run ID 搜索；部分成功 Run 的原因、影响和下一动作进入详情。Item 固定列列表按 `collectorId + entityKey` 聚合最新实体，展示实体身份、质量决定、变化与 Revision、发布时间、最近采集和 entity key；Collector 展示名与 Source host 相同时不得重复显示，并支持 Source、Collector、质量决定及关键词筛选。Item 详情提供“数据内容、版本与观察、质量决定、来源与谱系”四个顶部任务视图，不常驻右侧证据栏；可读来源入口默认显示，完整 lineage ID 默认收起。
9. Collector 详情在顶部栏当前页面标题左侧提供可访问的箭头返回按钮，正文不重复返回文字链接。批量导入顺序不进入 Collector 名称或主标题，完整入口网址只在概览中展示一次。正文提供“概览、规则、采集配置”三个一级任务视图；待审核状态默认进入规则审核，其余状态默认进入概览，没有候选或活动规则时不显示规则 Tab。概览展示当前状态、入口网址、活动规则、运行范围、最近运行和最多五条最近结果；待审核规则首屏直接显示发布阻断、审核摘要和字段决定，字段审核与样本数据在同一视图内切换；已发布规则在规则页直接展示 Stage 01、交接、Stage 02、规则状态、采集流程、输出字段、验证结果和审核结论，不设置额外规则详情 Dialog；采集配置以摘要展示 Source 定义、规则编辑、定时运行和增量策略；定时运行支持启停、常用频率、自定义五段 Cron、下次运行提示和禁止重叠运行，规则编辑 Dialog 提供“规则编辑”和“JSON”两个 Tab，完整 GatherSpec 只在“JSON”中按需只读展示，内部版本 ID 与 digest 不作为独立信息项展示，且原始 JSON 不提供直接编辑入口。字段和 Item 证据默认不显示，点击对应信息后以可关闭、可独立滚动且焦点可恢复的右侧 Sheet 展示。两种支持视口均不存在不可达操作、文本遮挡或关键信息溢出。

11. 使用不可达 Source 触发探索时，Operation 以 `SOURCE_UNREACHABLE` 终结，错误信息包含 Source 主机、可理解的连接原因和检查动作，不包含 Crawl4AI/Playwright 堆栈或源码路径；可访问 Source 的列表发现、详情抓取与候选校验仍能完整通过。同域 iframe 外壳由探索解析为有效列表入口，发布后的 Run 必须执行 GatherSpec 冻结入口。

### `AC-016` 本地真实纵向闭环

**映射：** `FR-005`、`FR-006`、`FR-007`、`FR-009`、`FR-010`、`NFR-003`、`NFR-011`

1. FastAPI、Crawl4AI Explorer 与 Crawlee Runtime 分进程运行，API 请求生命周期不执行长任务。
2. SQLite WAL 持久化 Collector、Operation、Run、Item、leased job 与幂等响应；API 或页面刷新后读取同一事实，终态不回退。
3. 可重复本地 Source 经过两页列表、四个详情和 next_link 真实 HTTP 请求，终结为 3 accepted 与 1 rejected。
4. 操作阶段、分页指标、详情发现数量、质量摘要和恢复动作来源于 Worker 执行结果。
5. 发布事务持久化 RFC 8785 canonical rule digest、Ed25519 RuleAttestation、不可变 RuleVersion、活动指针和哈希链 AuditEvent；API 接受 Run 与 Worker 发出 Source 请求前分别验证固定证明、key 状态和 trust revision，篡改、Retired 或 Compromised key 均阻断运行。
6. 新 Run 的“质量与证据”视图优先展示规则证明、固定采集范围、结果集冻结和 Artifact 保留方式等可读结论；rule digest、policy digest、attestation ID、SigningKey、trust revision 与对象 ID 仅在默认折叠的技术信息中按需展示。本地 SQLite、文件型开发 key、显式获批的匿名 HTTP 和 sampled 文件只作为开发基线，不替代生产 PostgreSQL、Redis、对象存储、OIDC/RBAC、KMS/HSM 与集中审计验收。
7. 北京政府采购公告 Source 在匿名 HTTP 风险策略下完成探索、两阶段 RulePlan 编译、审核、发布和确定性 Run；编译结果明确列表/详情字段、语义绑定、identity 与 fingerprint，GatherSpec 固定 selector、分页和同源请求边界。直接公告入口的验收 Run `run_ff9e7e00acc1489a` 获取 `1` 个列表页和 `14` 个详情，得到 `14 accepted / 0 rejected`；增量 Run `run_c2c83dcb10594c44` 得到 `14 unchanged / 0 updated / 0 new`，RuleAttestation 为 `verified`。外层 `#shuju` iframe 场景还必须解析同域列表入口并完成首次窗口与增量 Run；每个 accepted Item 的标题必须是公告标题，不得是正文表格里的采购项目名称。
8. Collector 可保存不可变 CollectionPolicyVersion；首次 Run 使用滚动窗口，后续 Run 固定成功 Checkpoint 与回看窗口。连续旧页正常停止可以推进 Checkpoint，`max_pages`、`max_items`、失败或部分成功不得推进。Run 证据展示 policy digest、窗口、new/updated/unchanged、窗口外数量和 Checkpoint 前后值。
9. `PATCH /collectors/{collectorId}` 与 `PATCH /collectors/{collectorId}/candidate-rule` 符合 OpenAPI、幂等和并发阻断合同；候选编辑复用最近 Crawl4AI 探索 Artifact 做同步样本验证，旧 RuleVersion 的数据库不可变约束保持生效。

### `AC-017` AI 任务历史、重试与模型审计

**映射：** `FR-005`、`FR-020`、`NFR-001`、`NFR-002`

## 7. 缺陷严重度

| 级别 | 定义 | 发布规则 |
| --- | --- | --- |
| `P0` | 已发生或可直接造成跨租户、凭据泄露、不可恢复数据丢失、任意代码执行或全面不可用 | 立即停止发布与相关生产能力 |
| `P1` | 核心旅程不可用、错误数据/交付、不可审计高风险操作、SLO/RPO/RTO 明确不达标且无可接受绕行 | 必须关闭后发布 |
| `P2` | 非核心退化、局部可用性/体验问题或有安全且明确绕行的缺陷 | 必须有负责人、影响、目标版本和到期日 |
| `P3` | 不影响正确性与安全的轻微问题 | 可进入常规 backlog |

## 8. 证据要求

每个 `AC-*` 必须具有：

- 候选构建 digest、环境和执行时间。
- 测试命令或自动化 job 标识。
- 原始结果、通过/失败摘要和已知限制。
- 关联缺陷及其处置。
- 责任人复核结论。

证据不得由纯文字“已通过”替代。失败测试不能删除或跳过来获得通过状态；例外必须由验收责任人明确接受并设置到期日。

## 9. 发布退出条件

1. `AC-001` 至 `AC-017` 全部通过。
2. 功能、非功能、安全和灾备证据完整且可复现。
3. P0/P1 缺陷为零，P2 缺陷具有用户影响说明和明确处置版本。
4. 监控、告警、暂停、回滚和事件响应路径完成生产前演练。
5. 发布、数据库和规则回滚路径经过验证。
6. 产品负责人和技术负责人明确签署 `Accepted`。

### 概览看板验收

概览看板同时显示今日采集、本周运行成功率、本月有效数据和当前规则覆盖，不得用单一周期切换替代这些并列口径。日、周、月只控制采集产出趋势，分别形成最近 14 天、12 周和 12 个月的 14、12、12 个时间桶；柱形区分接收与拒绝数据。运行质量面板随趋势口径更新成功率、成功/部分成功/失败分布与数据通过率，需要关注面板最多显示三项人工动作。聚合最多读取 200 条 Run 与 Item 观测，支持视口内无横向溢出或控件遮挡。

## 10. 发布后验证

- 上线后 24 小时验证租户隔离、RuleAttestation、调度延迟、Run 结果、Delivery 和告警。
- 上线后 14 天按 `KPI-001` 至 `KPI-007` 建立首个生产基线。
- 阻断级安全或数据正确性问题立即暂停相关能力并按已验证回滚路径处置。
- v0.2 验收证据至少保留 365 天。
