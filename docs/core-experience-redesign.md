# Extrio 核心体验重构方案

版本：v0.2 · 日期：2026-09-05 · 状态：单前端持续迭代，需求拆分与字段入口方向已确认

本文是产品与体验提案，不代表所有能力已实现。产品边界以 [SSOT](SSOT.md)、[产品合同](product-contract.md)、[前端合同](frontend-prototype.md) 和 [发布验收](releases/v0.2-acceptance.md) 为准。原型即正式前端迭代，使用同一入口与真实后端，不维护独立演示应用。

## 1. 核心判断

**重构目标不是增加页面或统一外观，而是让用户连续完成“定义需求、验证数据、稳定运行、消费结果”，并始终知道下一步该做什么。**

首批验证围绕持续采集公告的团队展开：配置人员负责接入，审核人员负责发布，运营人员负责异常处理，数据使用者负责查询与交付。角色可以由同一个人承担；现有公开或授权数据源范围保持不变。

| 当前断点 | 用户成本 | 重构方向 |
| --- | --- | --- |
| 需求分组与各来源输出字段之间缺少完整的共享合同闭环 | 同一需求的数据不一定可以直接比较和消费 | 用户确认业务字段，再冻结版本并绑定来源 |
| 配置、样本、规则、运行和数据分布在不同页面 | 用户需要记住上下文，自己拼接结论 | 跨页面保留需求、来源、版本与返回位置 |
| 审核需要理解较多规则和技术信息 | 难以快速判断“数据是否符合预期” | 业务样本优先，字段证据和选择器按需展开 |
| 异常可见，但原因与恢复动作衔接不足 | 网络失败、规则失效、交付失败容易被混为一谈 | 按影响和原因提供不同恢复路径 |
| 数据和运行列表默认仅取最近 200 条，列表与导出过滤语义不一致 | “看到什么、导出什么、总共有多少”缺少可靠对应 | 服务端统一查询、分页、统计与导出语义 |

以上是基于当前代码和桌面界面的诊断，不是外部用户研究结论。特别是分页问题属于前端消费方式，不代表后端没有分页能力。

## 2. 三条核心链路

| 用户故事 | 连续路径 | 用户获得的结果 |
| --- | --- | --- |
| UX-US-01：接入一个持续采集需求 | 描述需求或选模板 → 确认业务字段 → 冻结需求版本 → 添加来源 → 编译并验证样本 → 人工发布 | 明确采集什么、每个来源是否满足要求，以及发布的具体版本 |
| UX-US-02：恢复异常采集 | 查看需求健康 → 定位受影响来源与数据 → 判断原因 → 重试、修复规则或重新交付 → 验证恢复 | 不靠猜测选动作，知道恢复是否真正完成 |
| UX-US-03：使用可信数据 | 进入需求数据集 → 检查业务字段与新鲜度 → 筛选和比较 → 导出或交付 → 按需追溯 | 查询范围明确，输出与查询一致，结果可解释 |

数据字段提供选模板、描述需求后由 AI 建议、手动添加三种入口，最终进入统一编辑界面。模板与 AI 建议先预览，经确认后应用到草稿。用户可以新增、修改、删除业务字段，并定义名称、类型、必填、业务含义、单位和示例。示例不是采集证据；不符合要求的来源不能靠静默放宽必填字段通过验证。系统管理的采集时间、来源身份和运行编号不属于可随意编辑的业务字段。

草稿允许自由编辑。已确认定义保持不可变，修改通过下一版本草稿进行；确认新版本使受影响的候选需要重新验证与人工发布，不覆盖活动规则、历史结构或历史数据。显示名称与业务语义变更必须明确区分。

“已发布”“最近运行成功”“数据新鲜”“交付成功”分别表达，不合并成一个绿色状态。新鲜度应展示最近观测时间及判断依据，避免把“没有新公告”直接认定为采集故障。

## 3. 信息架构

一级入口为概览、采集需求、采集器、运行、数据、设置。不设置独立告警、调度或交付中心一级导航。

| 入口 | 页面职责 |
| --- | --- |
| 概览 | 回答哪些需求需要关注、影响是什么、下一步是什么；统计必须覆盖声明的数据范围 |
| 采集需求 | 业务主入口，承载需求目标、数据字段、版本、来源覆盖与需求数据；用户从需求工作区添加来源 |
| 采集器 | 跨需求的来源运维入口，承载来源规则、运行配置与异常处理；与需求内来源列表复用同一个采集器详情 |
| 运行 | 承载执行历史、失败诊断、恢复动作和恢复结果；AI 编译仍是辅助视图 |
| 数据 | 以需求数据集为主要消费视角，支持来源、版本和业务条件筛选，以及导出与追溯 |
| 设置 | 承载模型、凭据、交付连接等配置，不承担日常任务入口 |

需求对应 `Collection`，字段合同对应不可变的 `CollectionVersion`，来源仍由独立 `Collector` 执行。需求上下文不是新增一套并行领域对象；跨来源汇集不意味着合并来源的检查点、失败域或交付身份。

首批保持一个 Collector 归属一个需求，不建设跨需求共享执行实例。界面使用“数据字段”“确认字段并添加来源”等业务用语；合同是内部约束，不是要求用户先理解的工程概念。

筛选、排序、分页和选中对象应可通过 URL 恢复。不同合同版本的数据不得无提示地混成同一字段结构；跨需求视图仅展示公共元数据，具体业务字段进入相应需求与版本查看。

## 4. 四个关键工作面

### A. 需求接入工作区

- 布局：顶部阶段导航，主体为当前阶段编辑区；需求字段与来源验证结果可随时回看。复杂编辑使用完整工作区，不塞进多层弹窗。
- 主动作：确认字段、冻结版本、验证来源、进入审核。每一步只有一个明确的主动作，不以配置完成冒充采集成功。
- 状态：草稿可恢复；批量来源逐项呈现成功、失败与待处理，单项失败不吞掉其他结果；缺少模型配置时给出明确配置入口，不生成伪验证结果。

### B. 规则审核工作区

- 布局：业务样本表为主体，突出缺失、类型不符和列表详情不一致；选择字段后按需打开证据侧栏，选择器和只读 JSON 放入高级视图。
- 主动作：确认当前候选版本并发布，或修改后重新验证。发布必须绑定实际审核的字段合同、规则版本与验证结果。
- 状态：验证失败、编辑未验证、候选已变化和权限不足分别处理。必需检查未通过时不能发布，已发布版本不可原地修改。

### C. 异常恢复工作区

- 布局：先显示受影响来源、运行和数据范围，再显示原因、建议动作与证据。复用运行详情和采集器详情，不先建设独立告警平台。
- 主动作：临时获取失败走运行重试；规则失效走候选修复、验证和审核；交付失败走有权限约束的重新交付。
- 状态：明确部分成功、等待恢复、恢复中和恢复验证结果。首批不承诺仅重跑失败页面；未完成运行不得推进检查点，重复点击不得造成重叠运行或无意重复交付。

### D. 需求数据工作区

- 布局：需求与版本上下文、固定查询工具栏、业务字段表格、按需打开的详情和溯源侧栏。标题、时间和核心业务字段优先，技术标识可查看但不占据默认视觉中心。
- 主动作：筛选、查看变化、导出与交付。列表、数量和导出使用同一查询定义；导出明确范围，采用固定快照或截止点避免新数据造成范围漂移。
- 状态：无数据、无匹配结果、加载失败、数据陈旧和交付失败不能共用一个空状态；分页不能让用户误以为最近一批就是全部数据。

## 5. UI/UX 约束

- 桌面专用：主验收视口 `1440×900`，最低 `1024×800`，补充 `1280×800` 与 `1132×1028`，不纳入移动端适配。
- 使用密集但可扫描的操作界面：稳定列宽、紧凑工具栏、明确状态与动作；不使用大面积欢迎区、营销式大标题或嵌套卡片。
- 表格、筛选、标签页、侧栏、确认框采用统一交互规则；简单命令用弹窗，复杂编辑用工作区，补充证据用侧栏。
- 加载与异步状态保留布局和输入；操作后明确说明影响对象及结果，不仅显示短暂的“成功”提示。
- 中英文长文本、键盘操作、可见焦点和非颜色状态提示纳入验收；普通文本对比度目标至少 `4.5:1`。
- 字体、间距、行高和色彩先复用现有设计基础，通过四个工作面的连续原型验证后固定，不先做全站换肤。

## 6. 实施顺序与边界

| 批次 | 交付边界 | 关键依赖与退出条件 |
| --- | --- | --- |
| B0：修复数据可信性断点 | 列表分页、搜索、数量和导出语义对齐；明确统计范围 | 确认后可独立实施，不等待视觉重构；超过 200 条的数据仍可完整查询，导出符合过滤范围 |
| B1：需求到人工发布 | 共享字段合同、草稿恢复、来源接入、样本审核，完成工作面 A/B | 先落实字段合同与来源绑定的数据/API 约束；新需求可走通，历史来源不被自动改写 |
| B2：数据到交付 | 完成工作面 D，并将 B0 查询能力接入需求与版本上下文 | 保留现有交付协议与来源身份；列表、导出和交付范围可验证 |
| B3：异常到恢复 | 完成工作面 C，再由真实运行与数据状态组织概览 | 区分获取、规则和交付故障；恢复结果可验证，概览不依赖最近 200 条推算全量健康 |

每批包含自身的错误态、权限控制和回归测试，不把基础异常处理拖到 B3。首批场景采用一个公告字段模板和两个来源，其中一个可正常通过，另一个用于验证失败恢复。

关键依赖是领域合同与界面同步设计：相同 `CollectionVersion` 标识不能替代输出结构校验。历史来源先检查兼容性，不匹配项进入人工确认和新候选验证；历史规则与运行证据保持不变。API 以兼容扩展为优先，破坏性变化需单独确认迁移方案。

**本轮不做：**模板市场、跨来源实体合并、独立告警平台、全站品牌升级、移动端、运行时 LLM 自主修改规则、自动发布，以及与三条核心链路无关的新功能。

## 7. 验收目标

以下是后续实施的验证要求，不是已经完成的测试结果。

| 编号 | 验收场景 |
| --- | --- |
| UX-AC-01 | 对应 US-01/B1：用户不写选择器即可通过模板完成两个来源的接入与样本检查；失败来源独立显示原因，成功来源仍需人工审核发布 |
| UX-AC-02 | 对应 US-01/B1：同一需求版本的来源遵守相同字段和类型要求；合同变更生成新版本，编辑未验证或候选过期不能发布 |
| UX-AC-03 | 对应 US-03/B0/B2：使用至少 501 条数据和 301 条运行记录验证完整分页；标题、来源等支持的筛选条件下，列表、计数与导出记录范围一致 |
| UX-AC-04 | 对应 US-02/B3：分别注入网络失败、规则不匹配、交付失败，用户可选对恢复路径；部分失败不推进检查点，恢复结果及副作用可追踪 |
| UX-AC-05 | 跨链路：刷新可恢复约定的草稿和查询上下文；无权限用户无法发布或重新交付；重复提交和过期版本有明确保护与反馈 |
| UX-AC-06 | 跨链路：两个桌面视口、中英文和键盘操作下，无关键文字遮挡或不可达动作；邀请 5 名目标用户测试，至少 4 人无需指导完成对应角色核心任务，并记录操作、等待和补救耗时 |

除完成率外，持续记录首次有效数据耗时、审核返工次数、异常恢复耗时和导出范围不一致次数。字段准确性、漏采率与新鲜度通过标注样本和实际运行另行验证，不能用界面完成度或签名溯源替代。

## 8. 评审与下一步

建议本次确认三项决策：

1. 需求与采集器分设一级入口；需求定义数据目标，采集器执行来源规则，数据页面保留共同需求上下文。
2. 以业务字段和样本为主界面；共享合同先确认，技术规则按需展开，人工发布边界不变。
3. 按 B0、B1、B2、B3 排序；原型贯通三条链路，代码按批次交付，概览视觉重构最后进行。

需求拆分、三种字段入口与字段编辑方向已获得用户确认，当前授权覆盖独立连续交互原型。真实 AI 字段建议、持久化字段版本 API、来源迁移与生产发布仍需首批技术实施范围和验收清单。原型中的 AI 建议为明确标记的本地模拟，不代表真实模型能力。

进入实施前，将已确认范围同步到 `docs/SSOT.md`、`docs/product-contract.md`、`docs/frontend-prototype.md` 和 `docs/releases/v0.2-acceptance.md`；涉及字段合同、查询或副作用的变化，同时更新相应领域与 API 合同。本文不单独覆盖这些权威定义。
