# 1.0 全站体验工作流

日期：2026-09-06。状态：体验目标已确认，D1-W1、D1-W2 与 G1 已工程交付，等待用户页面复核。现有核心页面完成批量走查与修复；新增功能界面归 G2/G3，最终跨流程验收归 G4。本文件规定覆盖范围和执行方式，不授权一次性重写全站。

## 目标与原则

Extrio 1.0 同时满足功能可靠和操作体验成熟。页面打磨覆盖内容取舍、信息顺序、桌面布局、跨页上下文、操作反馈和视觉细节，不限于字体、颜色或间距。

- 页面围绕用户要做的工作组织，而非简单展示后端对象及全部字段。
- 首屏回答当前对象或工作是什么、结果/状态如何、下一步能做什么；技术 ID、完整合同和诊断细节按需展开。
- 列表支持定位和比较；详情支持判断和操作；编辑界面支持完成任务且保留错误后的输入。
- Tab 用于不同任务视图；Dialog 用于有边界的编辑/确认；Sheet 用于不打断上下文的证据查看。不为了视觉统一把所有操作塞进同一种容器。
- 不以增加卡片、隐藏必要信息或缩小字号制造整洁。保留高密度运营控制台定位，不做营销式大屏或移动端。
- 异步等待、取消、部分失败、权限不足、并发冲突和离开未保存页面，与成功状态一起设计。
- 所有改动进入当前正式前端；未实现后端功能明确标识，不使用模拟成功填补设计。

## 页面与流程覆盖

下表以 `web/src/app/router.tsx` 为页面清单，检查方向是待验证的设计问题，不代表已观察到的缺陷。

| 页面/流程 | 需要回答的问题 | 优先批次 |
| --- | --- | --- |
| 全局导航、顶部栏、返回与跨页上下文 | 对象层级是否清楚？返回是否保留筛选？主要动作位置是否稳定？ | 代表性页面前建立共同规则 |
| 需求列表与新建 `/collections`、`/collections/new` | 能否找到和区分需求？新建是否只收集必要信息？ | A |
| 需求详情、字段编辑 `/collections/:id` | 业务目标、草稿、已发布合同和来源差异是否易分辨？ | A，优先形成样板 |
| 来源列表与批量接入 `/collectors`、`/collectors/new` | 批量输入、逐条错误、部分成功与需求归属是否顺畅？ | B |
| 来源详情、规则审核、配置 `/collectors/:id` | 哪些信息支持审核决定？探索、发布、运行和修复的入口是否符合状态？ | B，第二个样板 |
| 运行列表与详情 `/runs`、`/runs/:id` | 能否迅速理解成功/部分成功/失败、影响及恢复动作？ | C |
| AI 任务详情 `/ai-runs/:id` | 进度、失败阶段、可重试性、生成成功与发布状态是否分开？ | C |
| 数据列表与详情 `/items`、`/items/:id` | 能否找数据、对比变化、检查质量和可信来源、准确导出？ | C |
| 概览 `/` | 首屏是否服务日常运营决策，而不是重复列表或展示缺少行动价值的指标？ | D，依赖核心流程和全量统计 |
| 系统与模型设置 `/settings` | 配置分类、权限边界、凭据状态、保存反馈是否可理解？ | D |
| 管理员初始化、登录和会话失效 | 用户是否理解实例初始化？会话失效是否保留目标页面与安全边界？ | D |
| 全局空/加载/错误/权限状态 | 状态是否能区分，能否重试，输入与上下文是否保留？ | 每批必验，不留到最后 |

## 执行顺序

1. 真实页面走查：固定桌面尺寸，沿“需求 → 来源 → 审核 → 运行 → 数据”截图并检查关键状态，形成有证据的问题列表。设置、概览、登录独立补查。
2. 确定共同设计规则：导航、密度、标题/状态/动作层级、表格和表单、反馈与弹层边界；从实际问题出发，避免重新发明整套组件库。
3. 以需求详情和来源审核作为代表性页面给用户复核内容结构和交互方案。方案通过后再进入行为实现，不先全站改 CSS。
4. 按 A/B/C/D 流程批次落入正式前端，与字段发布/迁移等功能任务协同。每批包含关联列表、详情、编辑及失败状态，而非按孤立页面交付。
5. 每批验收后统一复查跨页流程和一致性。发现共同组件问题在所属组件修复，不逐页堆叠覆盖样式。

P04/P07/P10 等功能任务负责新增能力的完整可用界面；本工作流负责已有与新增界面的信息架构和体验质量。拆分工作包时明确唯一归属，避免重复估算同一次表单实现、状态处理或 QA。

## 体验完成标准

- 每个页面具有明确主要任务和动作层级，状态、阻断原因与下一步可找到。
- 代表性数据包含空数据、长中文/英文、真实复杂字段、大列表和失败记录，而不是只验收整齐样例。
- 搜索/筛选/分页、返回、刷新、深链接和跨页操作保留合理上下文。
- 编辑失败不丢输入；并发冲突不覆盖他人修改；危险操作有适当确认；异步状态不伪报完成。
- `1440x900` 为主视口，补验 `1280x800`、`1132x1028`、`1024x800`。必要宽表仅在自身区域滚动，关键操作不被裁切。
- 中文/英文、键盘焦点、弹层关闭与焦点恢复、非颜色状态表达均检查；截图不替代可访问性和行为测试。
- 相关测试、lint/build、真实浏览器证据与用户页面复核共同作为交付条件。用户确认页面方案与接受实现分别记录。

## 估算边界

1.0 交付按 4 个约 3 小时大工作包组织，G1 已工程交付；剩余 G2–G4 暂保留 9 小时执行目标，按具体缺口保留 1–2 个补充包。G1 的约 75 分钟支持批量组织现有页面改进；G2 的字段模型和迁移仍需实测校准，不按前端吞吐外推。完整分工和验收项见 [交付规划](v1.0-delivery-plan.md)。

D1-W1 和 D1-W2 的目标累计执行墙钟时间分别为 1,343 秒与 1,324 秒，合计约 44 分 27 秒；它们是两个局部体验样本，不是完整 3 小时容量测试。G1 将已有页面体验批量实施与验证，G2/G3 同步打磨其新增能力，不重复估算；G4 负责集成检查，不能代替前几包的设计和实现。每包记录实际用时、覆盖与残余风险，不能按路由数乘固定时长，也不能用预算不足为理由跳过交互状态、中英文或桌面验收。
