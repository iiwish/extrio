# 采集来源生命周期执行计划

状态：Confirmed / Needs_Review。CL-01 至 CL-04 已实现并完成工程验证，等待用户验收；不代表部署或产品签收。

来源删除采用已确认的[来源删除与历史保留计划](source-deletion-plan.md)。本计划的归档、恢复、定义编辑与跨需求归属边界保持有效；删除验收以该专项计划及当前产品合同为准。

## 需求与边界

用户已确认补齐来源新增、编辑、空白删除、归档恢复，并将调整所属需求作为独立操作。本计划明确这些操作的数据和运行边界。用户已批准按本计划执行。不修改用户来源、不部署、不删除测试库以外的数据。

沿用 AGENTS.md 的单前端、桌面范围、pnpm 和已有工作区保护规则。当前工作区有大量在途改动，只在既有代码上增量实现，不重置文件或重建数据库。

## 操作合同

1. 新增沿用需求内弹窗和来源工作面的批量入口，需求内新增固定 Collection ID。
2. 基本信息编辑保持独立入口；URL 或采集目标改变后停止调度并要求重新探索、审核发布，不允许复用旧规则继续执行新定义。历史规则、运行、数据保留原始内容。
3. 永久删除仅用于空白来源：没有探索、AI 任务、规则、运行、数据、迁移或对外投递历史。创建时自动生成的初始策略和禁用调度不算业务历史，可以在同一事务清理。存在其他关联时返回具体阻断原因，不能级联删除历史。
4. 归档保留来源 ID、规则、证据、运行和数据；默认活动列表隐藏，已归档筛选可查看。归档原子关闭调度，归档来源禁止新增探索、修复、发布、手动运行及调度启用。
5. 排队中、已领取或正在执行的来源任务均阻止删除、归档和调整归属。服务端检查实际持久队列及运行状态，不只检查前端按钮或 activeOperationId。已领取的调度触发必须在创建运行前再次验证来源状态。
6. 恢复来源不自动开启调度、不启动运行、不重新发送历史投递。恢复后的可用操作由实际规则和版本状态决定。
7. 调整所属需求采用“目标选择、字段差异和影响预览、确认执行”的独立流程；只允许使用中的目标需求，不能选择自身，不能绕过运行中或迁移中阻断。
8. 空白来源可直接绑定目标需求。已有历史的来源调整归属后保留历史引用，停止调度，撤销旧规则作为后续执行依据的资格；按目标需求重新探索、审核发布。不得重写旧规则内的 CollectionVersion，也不得让旧运行或数据因当前来源归属变化而被解释为新需求的产物。
9. 已归档来源须先恢复再编辑或调整归属。归档保留 URL 占用；重复 URL 不创建第二个来源，不隐式合并、恢复或移动。
10. 所有破坏性或归属变更采用权限检查、预览摘要或 revision 乐观锁、数据库事务内并发校验、持久幂等回执和审计。工程师、管理员执行管理操作；审核发布保持现有角色边界。
11. 来源列表、详情和需求关联列表同步刷新；删除后返回原筛选列表。归档来源在需求详情仍可通过明确标记追溯，不计作可执行来源。
12. 来源归档不取消已产生的历史投递记录；正在投递的历史数据不视为新增采集，不改写其 payload 或目标。独立投递管理保持现有行为。

## 技术检查

- `app.py` 的定义修改接口仅重置 draft/candidate 等字段；生命周期需要同时约束调度与未来执行资格。
- `store.py` 的调度领取与 `app.py:create_run_operation` 分属不同阶段，归档判断必须覆盖两阶段并与来源锁协调。
- `collection_workflows.py:migration_plan` 明确仅支持同需求的字段版本迁移；跨需求调整不能直接套用现有接口或仅替换 collectionId。
- 现有 `collection_workflows.py` 提供事务幂等回执、审计和 PostgreSQL 来源行锁模式，可复用，但需统一锁顺序以避免与调度、发布和删除竞态。
- 生命周期与探索/发布状态分离，不能把 archived 混进探索状态机后依赖所有旧调用方自行理解。历史旧记录采用兼容默认值。

## 执行任务

按顺序直接执行，不委派；每个任务先写失败测试，再实现和验证。任务互相依赖，不并行修改共享合同。

### CL-01 后端生命周期

- 依赖：用户确认本计划。
- 文件边界：backend/src/extrio/{app,store,worker,collection_workflows,job_control}.py；新增来源生命周期模块；backend/migrations 下成对 SQLite/PostgreSQL 迁移；backend/tests 下生命周期、API、调度、并发测试。
- 实施：空白判定、删除/归档/恢复命令、预览及冲突校验、调度与所有采集执行入口保护、事务审计与幂等；清查 CLI/MCP 和内部调用，不允许绕过核心状态校验。
- 完成标准：有历史来源不可永久删除；活动任务阻断；归档与调度竞态不启动新任务；恢复不启用调度；重复命令不重复操作；失败不产生部分清理。

### CL-02 编辑与跨需求调整

- 依赖：CL-01。
- 文件边界：CL-01 后端文件；backend/src/extrio/{collection_fields,integrity}.py；必要的历史数据读取模块；相应迁移和 backend/tests。
- 实施：编辑后的调度/执行失效规则；跨需求预览、确认、固定目标合同、旧历史归属保护及新规则重建要求。
- 完成标准：目标变更使预览过期；归档目标拒绝；活动任务和未完成迁移拒绝；旧规则、运行和数据保持历史需求语义；新执行须经重新审核发布。
- 停止条件：历史归属无法可靠还原时，不猜测回填、不忽略关联；报告具体记录类型并提交最小补充决策。

### CL-03 API 与桌面管理体验

- 依赖：CL-01、CL-02。
- 文件边界：docs/contracts/{api-contract.md,openapi.yaml}；web/src/api；web/src/features/{collectors,collections}；相关 i18n、状态展示、样式及测试。
- 实施：来源列表/详情操作菜单，归档筛选、阻断原因、删除二次确认、恢复、独立归属调整预览；保持需求内新增流程及列表 URL 上下文。
- 完成标准：后端能力不可用不模拟成功；提交期间防重复和误关闭；失败保留输入；成功更新两侧需求和来源缓存；长文本及桌面最小尺寸可用；只读角色不出现可执行管理操作。

### CL-04 回归与交付证据

- 依赖：CL-03。
- 文件边界：docs/SSOT.md、docs/product-contract.md、docs/frontend-prototype.md、docs/releases/v0.2-acceptance.md、文档清单、docs/reviews/collector-lifecycle/。
- 命令：backend 中 `uv run pytest`；web 中 `pnpm api:generate`、`pnpm test`、`pnpm build`、`pnpm lint`；文档清单更新及检查；`git diff --check`。
- 数据库：SQLite 必测；PostgreSQL 使用隔离测试库，不能对用户当前数据库做删改验证；无法运行时明确标注，不宣称双数据库完成验收。
- 浏览器：隔离数据完成新增、编辑、空白删除、归档、恢复、归属调整、运行中阻断及失败重试；1440x900、1280x800、1132x1028、1024x800 截图检查。
- 证据：各任务记录实际变更、RED/GREEN 结果、并发反例、命令退出结果、桌面截图与剩余风险；未获用户验收不标记 Accepted。
