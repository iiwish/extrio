## Checklist 与 Analysis

- 身份与状态权威：固定 Run/规则/字段版本、数据库 job attempt/租约、稳定 Delivery ID、不可变审计/签名，UI 不是权限边界。
- 领取、续租、取消、终态、数据/Checkpoint/交付写入必须拒绝过期 Worker；同一逻辑运行重放不重复修订或遗漏交付。取消/超时是有证据的终态。
- HTTP/浏览器抓取在入口、跳转、网络及凭据边界失败关闭；支持约 12 个固定样本，不把任意站点兼容写成验收结论。
- readiness 区分 API 活着与 Worker 能工作，诊断只给有限状态/实例标识，不向普通用户泄露路径和凭据。
- 全量备份包含数据库、Artifact 和 key，明确停写条件、完整性和恢复目标；失败不能覆盖已有实例或偷偷生成新钥匙。恢复后验证解密、签名、历史版本和数据。
- 重放严格服从证据等级与有效性；规模报告包括实际条数/延迟/环境，不将平台容量目标当作实测。
- 已确认缺口：普通 job 领取缺少 PG 行锁/过期写入防护；Run 数据与 Delivery 入队分离；现有备份只包含数据库。优先构造反例，不把既有绿色单测当作灾备/崩溃证明。

## 诊断界面约束

现有控制台的局部完善（Standard），面向管理员和采集工程师，保持桌面密集布局、现有字体和中性背景；状态沿用绿色成功、琥珀警告和红色失败。运行页顶部提供真实取消命令和等待停止状态；设置的系统页以无外框的信息段显示 Worker 存活、部署匹配、排队数量和等待时间。证据视图采用真实完整性/有效期状态，不把终态或固定百分比当作证据。使用现有 Lucide 图标、32px 控件、12–14px 辅助文字、8/16px 间距，状态色不承担唯一信息。轮询变化不重排布局，加载/失败/重试/空 Worker 状态均有落点；不加营销图、卡片套卡片或移动端工作。验证包括取消待处理/终态刷新、缺失/到期证据和不匹配部署的组件测试，以及四个受支持桌面视口。

## 验证方式

行为修改先写失败测试并记录 RED，再修复、聚焦 GREEN、相关全套。已有功能可以通过反例/集成验证满足条目，不虚构 RED。SQLite 临时数据库与本机隔离 PostgreSQL 每测试独立数据库；不使用用户业务对象。

命令采用 `uv run --project backend pytest ... -q`、双数据库后端全套、`pnpm --dir web test --maxWorkers=1`、`pnpm --dir web build`/`lint`/`api:generate`、manifest 和 diff 检查。涉及前端时使用 1440x900、1280x800、1132x1028、1024x800；不测试移动端。单独记录真实本地网络/浏览器、子进程崩溃、CLI 空实例恢复、Compose 和规模测试，不能只用 Mock 代替。

每个 P 条目在统一验证记录中关联实际测试或演练；未通过保持未完成。范围符合性、缺陷安全/生命周期、QA 依次 review。工程验证完成推到 Needs_Review，用户产品签收与 G4 发布候选独立。
