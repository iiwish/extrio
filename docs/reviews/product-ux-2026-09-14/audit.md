# Extrio 产品体验诊断与设计建议

日期：2026-09-14。性质：基于当前本地实例的产品/UX 审查与待确认建议，不是已批准的范围变更，不替代产品合同。

## 结论

Extrio 有真实产品底座，但主体验仍偏向采集系统的操作与验收界面。用户能验证某次任务跑通，却需要自己跨页面拼出“我的数据需求是否满足、是否持续更新、哪里不完整、如何使用结果”的答案。

“像 demo”的主要来源不是配色不高级，而是工作主线、完成定义和信息优先级不够成熟。优先级应为：结果与信任语义 > 连贯工作流 > 数据使用效率 > 视觉一致性 > 装饰与品牌细节。

值得保留的核心方向是：AI 辅助接入、人工审核发布、确定性执行、可追溯数据。不要为了显得先进而改成通用 Agent 聊天框，也不要为了显得完整而扩张为通用爬虫、BI 或多租户平台。

## 用户与产品主线

建议以“对一组持续更新数据负责的数据运营人员”为主要设计对象。他们理解来源、字段和业务质量，但不应必须理解 CSS selector、编译阶段或内部对象 ID。数据消费者与接入工程师是不同工作模式，不必拆成两套产品。

用户目标应表述为：**把指定来源变成持续更新、质量可判断、可以交付的数据集。**

其中有三条应独立成立的旅程：

1. 首次接入：指定来源和需要的数据，检查真实样本，审核发布，取得首批可用结果。
2. 日常运营：确认更新是否按预期完成，只处理真正需要干预的问题。
3. 数据消费：按业务范围定位、比较和导出数据，必要时追溯某个字段的来源与变化。

当前第一条的后端环节较丰富，第二、第三条在界面中的地位偏低。

## 主要发现

这里的 P1 表示优先解决的产品风险，不表示已证明底层数据损坏；P2 表示效率与表达问题。

### P1：业务需求没有成为持续工作的中心

**证据：** 图 02 的需求列表主要展示意图、来源发布数、更新时间和合同引用。图 03 的需求详情只有“采集字段、关联来源”两个视图，默认进入字段。图 11 的数据页按域名、来源、质量筛选，没有需求筛选或需求内数据视图。

**影响：** 用户创建“标讯测试”后，不能留在这个业务上下文中检查结果、确认覆盖、查看异常或使用数据。需求更像配置对象，而不是用户回来工作的地方。

**建议：** 在既有 Collection 身份下建立业务工作台，包含“数据、来源、字段、活动/交付”等任务视图。已有数据时默认数据或运营结果，未接入时默认下一项接入任务。全局来源、运行、数据页保留为跨需求运营工具。导航是否把“采集需求”改成“数据集”，应与真实用户验证，不把改名当作完成重构。

代码锚点：[需求分区默认值](/Users/iiwish/self/extrio/web/src/features/collections/collection-page.tsx:47)、[需求页两个分区](/Users/iiwish/self/extrio/web/src/features/collections/collection-page.tsx:94)、[数据筛选模型](/Users/iiwish/self/extrio/web/src/features/items/items-page.tsx:34)。

### P1：绿色状态没有表达需求是否兑现

**证据：** 图 03 显示“v2 当前生效”和“来源发布 1/1”，四个字段均显示来源覆盖 1/1。图 14 才显示实际来源“v1 → v2，未对齐”。图 05 显示“采集来源已就绪”，图 07 中该来源却是“仅手动运行”。图 08 使用“完整成功”筛选，图 09 中同一次成功运行又明确说明“尚未确认采集范围已全部覆盖”。

**判断：** 这些状态可能在各自工程定义上成立。来源继续执行旧版本也可能是正确的冻结规则行为。问题是界面没有让用户自然区分它们，容易把已发布、已生效、已运行、已采全、持续运行理解成一回事。

**建议：** 分开表达四类事实，不制造一个万能健康分：

- 规则资格：待审核、可执行、待迁移。
- 最近执行：未运行、运行中、成功、部分完成、失败。
- 数据状态：最近更新、字段质量、范围覆盖已确认/未确认。
- 持续交付：仅手动/已启用计划、下次运行、交付配置与结果。

需求页摘要应直接说明“目标 v2，1 个来源仍执行 v1”，并提供对齐入口。页数限制是正常终止条件时保留成功，但不要用“完整成功”暗示已采全。没有新鲜度目标时只报告时间，不凭日期推断“已过期”。

### P1：待处理数量与进入后的集合不一致

**证据：** 图 01 显示 4 项需要人工推进，“查看全部”指向来源的需处理筛选；图 04 的来源列表只计入 3 项。代码确认首页纳入“已发布但无首次运行”的来源，而来源列表 `needsAttention` 未纳入同一状态。

**影响：** 用户点击“全部”会失去一项工作。这是可定位的跨页一致性缺陷，不只是视觉偏好。

**建议：** 对“待接入、待审核、首次待运行、执行异常、字段待迁移”采用共享分类和集合定义。首页总数与目标筛选保持一致；运行历史异常数与当前待处理来源数不同，必须用不同名称。历史失败不要自动等同于当前未解决问题。

代码锚点：[首页首次运行待办](/Users/iiwish/self/extrio/web/src/features/home/home-page.tsx:64)、[来源列表待处理定义](/Users/iiwish/self/extrio/web/src/features/collectors/collectors-page.tsx:54)、[首页查看全部](/Users/iiwish/self/extrio/web/src/features/home/home-page.tsx:185)。

### P1：异常解释存在，但恢复仍需要用户自行推理

**证据：** 图 12 同时出现 2 条接收、9 条拒绝、8 个详情未抓取。页面提示检查访问或网络后重试，主要操作却是“查看拒绝项”和“修订采集规则”。前者实际链接到第一条拒绝数据。列表中的拒绝原因是标题不一致，与 8 个未抓取页面属于不同问题类别。

**影响：** 用户知道不正常，却不知道哪些应重试、哪些应修规则、已保存数据是否受影响，以及操作是否会重复交付。错误说明没有直接转化为可完成的处理流程。

**建议：** 先显示“已保存 2 条；9 条质量不通过；8 个页面未获取”的独立分组，再逐组展示影响、证据、允许执行的动作。网络问题不默认引导改规则；质量问题直接对照冲突字段。现有入口先准确命名并定位；“仅重试失败页面”等能力需要后端支持、幂等与交付验证，不能只做一个看似可用按钮。

### P1：采集结束之后，数据仍像系统记录

**证据：** 图 11 为 Entity key 保留整列，真实公告标题大量截断；变化、Revision、观察次数占据显著位置。需求定义的业务字段没有成为可选择的表格列。图 10 可读正文存在，但顶部重复占用空间说明“规范化数据可用”和版本等系统信息。图 09 的 200 条结果直接逐条展示，没有本次结果的搜索/筛选/导出操作区。

**影响：** 用户要回答业务问题，仍需逐条进入正文或导出后在外部整理。产品的价值在“证明已经采到”处停住了。

**建议：** 在同一需求范围内按已声明字段展示数据，支持列选择、业务日期筛选、排序和全文检索；把质量异常做成专门视图，把 ID 放进详情。保留全局运营记录视图，但不要把它当作所有数据消费者的默认界面。字段不存在时显示未提取，不擅自从正文制造值。大表格能力需要服务端按相同字段与筛选导出，不能只筛选当前加载页。

### P2：规则页优先解释系统，而非帮助判断输出

**证据：** 图 06 的已发布规则页主体为两个阶段、selector、detail URL 样本及质量终结链。真实字段值、原始证据对照和发布责任没有成为主内容。代码中的已发布 `ValidationWorkspace` 仅组合摘要与 `CollectionFlow`；待审核 `ReviewWorkspace` 已有字段和样本能力，不能说整个产品没有样本审核。

**影响：** Extrio 最有差异化的“可验证”被表达为技术说明，而不是一种低成本的判断能力。大量术语、阶段卡片、说明文字容易带来技术演示感。

**建议：** 规则工作区以“提取结果与证据核对”为核心：字段及样本为主体，选择某字段时展示对应的不可变来源证据、缺失/冲突和变更。已发布后保留只读回看；selector、GatherSpec、签名摘要作为工程层。没有可用快照时明确标注，不能把当前网页冒充历史证据。

### P2：首次接入为批量配置优化，而非首次获得可信结果

**证据：** 图 13 在已有 6 个需求时仍默认“新建需求”。首屏需要先理解归属需求，再看到 CSV/TXT 格式、1000 行限制、字段名和精确列表入口。图 03 同时常驻模板、AI 建议、来源生成、版本历史、编辑、发布六种操作；已发布字段无改动时发布按钮仍可打开。

**影响：** 新用户最容易理解的行为是提供一个来源并看样本，但界面让他先承担组织对象和配置方式选择。日常操作者看到多个同权重入口，也难知道哪一个是当前应做的事。

**建议：** 默认单来源路径，批量接入为明确的另一模式；从需求内接入自动继承上下文。无上下文时展示已有需求的选择，不暗中替用户选错归属。渐进收集来源、字段意图、样本确认、运行/交付设置；可以跳过自动化，但必须标记“仅手动”。样本未经获取不能预填为成功，发布仍保留人工确认。

代码锚点：[创建默认模式](/Users/iiwish/self/extrio/web/src/features/collectors/new-collector-page.tsx:39)、[字段发布入口](/Users/iiwish/self/extrio/web/src/features/collections/collection-fields.tsx:145)。

### P2：视觉体系整洁，但信息密度与认知密度不匹配

**证据：** 图 01 是居中的图表工作台，图 02 为铺开的规格列表，图 06 采用卡片嵌套，图 10 为重复摘要后的正文阅读。业务标题被截断而技术 ID 保留；多处中英文技术表达混排。图 15-17 的字段操作条能换行，没有整页水平溢出，但仍常驻六个动作。

**判断：** 不是“没有设计”，而是页面分别打磨后，缺少共同的内容取舍原则。压小字或减少间距不能解决这一点。

**建议基线：** 正文/表格主信息 14px，辅助信息 12px，对象标题 20-22px；日常控件 32px 左右，表格常规行 48-56px，长标题允许两行。保留中性灰白底色，蓝色表示操作，绿/黄/红表示明确状态。统一页头、工具条、空状态和抽屉，不统一成到处都是卡片。上述数值是候选设计基线，不是已批准 token。

## 建议的页面组织

不必马上改路由或重新设计领域模型。先利用现有正式前端和 Collection，把分散的任务串起来。

| 表面 | 默认回答的问题 | 应占主要空间的内容 | 按需查看 |
| --- | --- | --- | --- |
| 工作台 | 今天需要我处理什么？哪些数据没有按预期更新？ | 按影响排序的待办、需求更新状态、有限产出摘要 | 历史趋势、运行统计 |
| 需求工作区 | 这组数据是否满足我的目标？ | 数据、最新更新、来源覆盖、未对齐/未解决问题 | 字段合同、历史与交付 |
| 来源详情 | 这个入口现在如何工作？ | 业务名称、入口、最近运行、实际范围、调度状态、最新结果 | 接入定义、规则编辑、AI 日志 |
| 样本与规则核验 | 这个字段为什么能信？ | 真值样本、来源证据、差异、审核决定 | selector、完整合同、签名元数据 |
| 运行详情 | 这一次交付了什么，剩下什么？ | 结果、未完成集合、原因分组、恢复动作 | 执行轨迹、预算、技术 ID |
| 数据详情 | 这条数据是什么，哪里变化了？ | 业务字段与正文、必要的来源/质量提示 | 版本比较、质量证据、完整谱系 |

最有辨识度的交互建议不是聊天，也不是漂亮图表，而是：**点一个字段，就能对照它的提取值、来源证据和变化。** 这能让确定性与可追溯性成为用户可感知的优势。

### 三个优先样板

1. **需求数据工作区。** 用本次“标讯测试”的真实 200 条结果，检验“看数据、找缺口、确认版本、启用持续更新”的连贯性。无数据时才是接入流程，不把字段编辑当常态首页。
2. **样本与规则核验。** 先呈现真实样本与字段差异，再提供审核/修复。已发布和待审核共享同一内容模型，已发布状态只读，不能隐式改规则。
3. **部分失败处置。** 用已有 2/9/8 的案例区分获取失败与质量拒绝，显示各自行动及历史，先完成现有能力可支持的路径，再评估失败子集恢复。

这三处定好后，再扩展到工作台和全站视觉规则。不要先全站换肤，也不要为方案另起一套静态 demo。

## 现有能力与新增依赖

| 建议 | 类型 | 边界 |
| --- | --- | --- |
| 待办口径一致、首次待运行可达 | 修正已有行为 | 首页与来源筛选共享规则并补回归 |
| 未对齐版本上提、仅手动状态上提 | 重组已有信息 | 不改历史版本和冻结执行语义 |

## 开源采用体验

仓库已经有安装步骤、Apache-2.0、贡献指南、路线图和成熟度声明。不能把差距概括为“补 README、补 CI”。当前 README 也明确不宣称外部用户验证和公开规模证明；本轮没有外部采用数据。

建议把世界一流开源的目标转成可验证的采用路径，而不是页面数或功能数：

- **第一次理解：** 项目首页用一个明确场景展示“输入来源、取得结构化数据、定位一条证据”，技术边界放在紧邻位置。不要只陈列系统能力。
- **第一次成功：** 一条稳定的隔离示例，带已声明的正确字段和失败样例；另有真实来源测试，不能混成一个通过率。让新用户在不理解内部术语时完成首次可用结果与导出。
- **第二周继续使用：** 能看出仅手动还是自动、更新是否按预期、异常是否已经解决。单次采集成功不是留存证据。
- **放心接入：** 明确支持/不支持的页面类型、模型依赖、成本/预算、数据安全、升级与恢复边界。用可复现兼容性语料和真实试用记录说话。
- **能够贡献：** 给出一条具体的“新增一个来源兼容性样例”路径，包含入口要求、期望输出、证据脱敏、回归命令和评审标准。不要要求初次贡献者先理解整个编译/签名架构。

优先邀请 5 位目标用户独立完成同一任务，记录卡点而不是只征求“好不好看”。这是建议的试验规模，不是已经取得的验证结论。不把多租户、移动端、市场、可视化 DAG 或更多模型适配作为产品成熟的前提。

### 可借鉴的原则

- Apify 的官方首次运行教程把输入、执行、查看输出、导出组织成连续流程。值得借鉴的是结果可达性，而不是复制 Actor 市场或放弃审核边界。[Apify Run Actors](https://docs.apify.com/actors/running)
- Dagster 的官方入口明确以数据资产、谱系和可观测性解释产品。对 Extrio 的启发是把数据产物作为运营对象，而不是复制复杂编排。[Dagster Overview](https://docs.dagster.io/)
- Airbyte 的 schema 配置围绕具体连接内的流、字段和目的端组织。对 Extrio 的启发是配置应服务某个持续数据交付目标，而不是成为孤立页面。[Airbyte Configuring Schemas](https://github.com/airbytehq/airbyte/blob/master/docs/platform/using-airbyte/configuring-schema.md)

以上是从官方文档提炼的设计原则，不是对这些产品做过实机对比审查，也不代表它们已验证适合 Extrio 的用户。

## 推荐执行顺序与验收

### 第一批：把状态和下一步说对

统一待办集合；上提版本未对齐、仅手动、范围未确认；修正“完整成功”等歧义；让错误原因与入口一致；把内部 ID 和阶段说明降级。保留现有功能边界，避免连带重构。

验收：相同数据下跨页待办一致；用户能明确区分规则已发布、首次运行完成、字段版本对齐、持续运行开启；每个异常入口定位到正确集合或明确的单条样本。

### 第二批：完成一条结果优先的产品主线

先设计并复核三个样板，再在唯一正式前端完成需求内数据工作区、样本核验和恢复流程。新增 API 能力与界面同时交付，缺失能力不得假装可用。

验收：目标用户不用 CSS selector 即可完成支持来源的样本核验；离开重回页面知道工作进行到哪；能从需求直接找到结果、导出，并辨认不完整之处。统计首次可信结果时间、无协助完成率、错误恢复完成率，先建立基线再设目标。

### 第三批：用外部用户与开源证据验证

完成隔离示例、兼容性样例贡献路径、清晰支持矩阵和外部试用。将第一次成功、第二周持续使用、异常恢复和贡献者首次 PR 的证据分开。

验收不以“所有按钮都有了”或“截图不溢出”为止。产品验收应包含：用户正确理解当前状态、能完成业务任务、知道不能保证什么、无需作者陪同也能继续工作。

## 无障碍与证据限制

- 已见积极信号：导航和多处图标有可访问名称；状态结合文字与图标，不仅靠颜色；需求字段使用真实表格语义；最小支持视口的字段工具条能够换行。
- 风险：来源、运行、数据列表主要用整行链接表达多列信息，部分列头对辅助技术隐藏，列含义关联需要屏幕阅读器实测；较小次级文字和弱对比说明可能影响长时间扫描。
- 未把小于某个字号自动认定为 WCAG 失败。控件实测多数为 28px 高、字段覆盖入口约 27px 高；目标大小、间隔、焦点与命名应结合完整交互测试判断。
- 已捕获桌面字段页没有整页水平溢出；关联来源表存在局部横向滚动。这不证明其余页面没有布局问题。
- 未测量完整颜色对比矩阵、200% 缩放、屏幕阅读器、键盘焦点循环、异步播报与错误恢复，因此不宣称无障碍合规。
